# AI랑 6년 전 코드 살리기 2편: 로그인을 지우고 분석 플랫폼으로

[1편](blog-post.md)에서는 2020년 Flask 프로젝트 **WGM.GG**를 TypeScript + Cloudflare Workers + Supabase로 되살려 `wgm.nori.day`에 배포했다.
원래 기능(전적 검색, 팁 게시판, 유저매칭, 회원가입)을 그대로 옮긴 1:1 이식이었다.

되살리고 보니 질문이 하나 남았다. **"이걸 누가 로그인까지 해 가며 쓸까?"**
그래서 2편에서는 로그인을 전부 걷어내고, Riot API 데이터만으로 **분석·챔피언 추천·장단점**에 집중하는 사이트로 갈아엎었다.

> 결과: **https://wgm.nori.day**

---

## 1. 요청은 두 문장

> 회원가입이나 로그인을 하지 않고 롤 api 만으로 통계 분석만 제대로 해주고 챔프 추천 및 장점 약점을 알려주는 특화 플렛폼으로 개션을하고싶어 이외 컨텐츠는 로그인 회원가입 하지 않고 사용할수 있는 것들로 알아서 만들어줬으면 좋겠고
>
> 디자인은 `npx getdesign@latest add coinbase` 를 사용해서 개선해줘

1편에서 얻은 교훈("결정은 먼저, 구현은 한 번에")대로 AI는 바로 코드를 고치지 않았다. **기획안과 질문 네 개**를 먼저 가져왔다.

| AI의 질문 | 내 선택 |
|---|---|
| 통계 데이터를 5분마다 자동으로 모을까? | **넣기** |
| 로그인 없는 콘텐츠로 무엇을? (티어표+챔피언 상세 / 소환사 비교 / 인게임 분석 / 최근 검색) | **티어표 + 챔피언 상세** |
| 안 쓰게 되는 팁·매칭 테이블은? | **삭제 SQL 제공** |
| 블로그는? | **2편으로 따로** (이 글) |

"알아서"라고 맡긴 부분은 AI가 정하고 이유를 남겼다. 인게임 분석은 한 번 보는 데 Riot API를 10번 넘게 불러서 개발 키 한도로는 자주 막힌다며 이번에는 뺐다.

## 2. 디자인: `getdesign`은 뭘 하는 도구일까

처음 보는 npm 패키지라서 AI가 실행하기 전에 패키지를 받아 소스부터 읽었다.

- [VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)의 CLI다.
- 하는 일은 **프로젝트 폴더에 `DESIGN.md` 한 장을 쓰는 것**이 전부다. 네트워크 요청은 다운로드 횟수를 세는 요청 한 번뿐이다.
- `DESIGN.md`는 색상, 글꼴, 간격, 둥근 모서리, 컴포넌트 규칙을 YAML 토큰과 설명으로 정리한 문서다. "UI를 쓰기 전에 코딩 에이전트가 이 파일을 참고하라"는 용도다.

이 템플릿의 핵심 규칙은 이렇다.

- 흰 바탕, **강조색은 파란색(`#0052ff`) 하나만**. 초록/빨강은 오르내림을 나타내는 글자색으로만 쓴다.
- 큰 제목은 굵게 쓰지 않는다(weight 400). 버튼은 전부 알약 모양, 카드는 24px 둥근 모서리.
- 어두운 전면 히어로 위에 제품 화면 카드를 겹쳐 놓는다.
- **숫자는 전부 고정폭 글꼴**로 쓴다.

AI는 이 토큰을 CSS 변수로 옮기고, 기존 MDB Bootstrap·jQuery를 전부 걷어냈다(정적 파일 약 8MB → CSS 16KB).
라이선스 글꼴 대신 문서에 적힌 대체 글꼴(Inter, JetBrains Mono)을 쓰고, 한글은 Pretendard를 붙였다. 화면 어디에도 원래 브랜드 이름은 쓰지 않았다.

전적 사이트는 숫자가 주인공이라 "숫자는 고정폭" 규칙이 특히 잘 맞았다. KDA나 승률이 세로로 딱 맞게 정렬된다.

## 3. 무엇을 만들었나

### 소환사 분석: 장점과 약점을 "같은 티어·같은 라인" 기준으로

![소환사 분석](screenshots/2026-v2/02-summoner.png)

최근 솔로랭크 20게임에서 지표 8개를 뽑는다. 승률, KDA, 킬 관여율, 분당 CS, 분당 골드, 분당 챔피언 피해, 분당 시야 점수, 분당 데스.
이 값을 **내 티어 구간 × 내 주 라인 평균**과 비교해서, 10% 이상 앞서면 장점, 10% 이상 뒤처지면 약점으로 보여 준다. 약점에는 개선 팁이 붙는다.

AI가 신경 쓴 부분이 두 가지 있다.

1. **주 라인 경기끼리만 비교한다.** 서포터로 한 판 한 경기의 CS를 미드 평균과 비교하면 억울하니까.
2. **비교 기준이 부족하면 지어내지 않는다.** 같은 구간 기록이 100명 미만이면 전체 티어 평균으로 바꾸고, 그것도 없으면 "비교 데이터 수집 중"으로 표시한다. 그럴듯한 기준값을 하드코딩하는 쪽이 쉬웠지만, 분석 사이트가 가짜 숫자를 쓰면 의미가 없다.

**추천 챔피언**은 세 갈래다.

- **주력 유지**: 주 라인에서 성적이 가장 좋은 내 챔피언
- **지금 메타 추천**: 내 티어 구간·주 라인에서 승률이 높으면서 **내 주력과 역할군이 같은** 챔피언 (Data Dragon의 Fighter/Mage 같은 태그 이용)
- **숙련도 활용**: Champion Mastery API에서 숙련도가 높고, 지금 메타에서도 괜찮은 챔피언

### 챔피언 티어: 하위 티어를 촘촘하게

![챔피언 티어](screenshots/2026-v2/03-tier-list.png)

2020년 원본의 목표는 "상위 티어 통계만 보여주는 전적 사이트는 하위 티어에게 도움이 안 된다"였다. 그래서 티어 구간을 **아이언–실버 / 골드–플래티넘 / 에메랄드–다이아 / 마스터+**로 나눠 따로 집계한다.

등급(S~D)은 그냥 승률이 아니라 **표본 수를 보정한 승률**로 매긴다. `(승 + 15) / (판수 + 30)`처럼 30판어치 50%를 섞는 베이지안 평균이다. 3판 3승 한 챔피언이 1위로 튀어 오르지 않게 하려는 것이다.

### 챔피언 정보: 장점·약점·카운터·빌드

![챔피언 상세](screenshots/2026-v2/04-champion.png)

- **장점/약점**: Riot 공식 능력치(공격·방어·마법·난이도, 0~10)와 **우리 데이터**(30분 이후 승률이 높으면 "후반에 강해요", 특정 상대에게 승률이 낮으면 "○○ 상대로 고전해요")를 함께 쓴다. 데이터에서 나온 문장에는 `데이터` 배지를 붙였다.
- **Riot 공식 팁**: Data Dragon의 `allytips`(이렇게 플레이하세요)와 `enemytips`(상대할 때는)
- 상대하기 쉬운·어려운 챔피언, 핵심 아이템, 룬, 소환사 주문, 게임 시간대별 승률, 스킬 설명

## 4. 설계에서 가장 크게 바뀐 것: 85KB를 버리다

1편에서는 match-v5 응답을 통째로 `jsonb`에 캐시했다. 자동 수집을 넣으려고 계산해 보니 문제가 보였다.

- 경기 하나의 응답이 **약 85KB**
- 5분마다 10경기씩이면 하루 약 2,900경기 → **하루 약 240MB**
- Supabase 무료 DB는 **500MB**. 이틀이면 가득 찬다.

그래서 원본을 버리고 **분석에 필요한 값만** 남기기로 했다.

```
matches            경기 1행: 시간, 길이, 패치, 표본 티어, 팀 오브젝트, 밴
match_participants 참가자 10행: 챔피언, 라인 상대, K/D/A, CS, 10분 CS, 골드, 피해,
                   시야, 킬 관여율, 딜 비중, 아이템, 룬, 주문 …
```

경기 하나가 약 3.5KB가 됐다(약 24배 감소). 30일이 지나면 Cron이 한 시간에 한 번 지운다. 이렇게 하면 많아야 300MB 정도에서 유지된다.

집계는 앱에서 하지 않고 **Postgres 함수**로 만들었다(`tier_list`, `position_benchmark`, `champion_detail`). Workers 무료 요금제는 요청 하나에 외부 호출을 50번까지만 할 수 있어서, 한 번의 RPC로 필요한 걸 다 받아 오는 게 유리하다.
테이블은 RLS를 켜고 정책을 두지 않았고, 함수는 `anon` 실행 권한을 뺐다. 로그인을 없앴으니 브라우저가 DB에 직접 닿을 이유가 없다.

### 자동 수집 (Workers Cron)

```jsonc
// wrangler.jsonc
"triggers": { "crons": ["*/5 * * * *"] }
```

5분마다 31개 구간(아이언 IV … 다이아 I, 마스터, 그랜드마스터, 챌린저)을 돌아가며 한 구간을 고른다. 그 구간에서 시즌 판수가 많은 40명 중 6명을 뽑아 **최근 14일 안의** 경기를 4개씩 보고, 새 경기만 최대 10개 저장한다.
한 번에 Riot API를 많아야 17번 부른다. 개발 키 한도(2분에 100회)의 일부만 쓰기 때문에 사용자 검색과 부딪히지 않는다.

## 5. 막혔던 부분

| 증상 | 원인 | 해결 |
|---|---|---|
| Riot API가 `403 error code: 1010` | AI가 파이썬 기본 User-Agent로 테스트해서 Cloudflare 봇 차단에 걸림 | User-Agent 지정 (Workers에서는 문제없음) |
| 상단 검색창이 위로 8px 치우침 | 페이지에 `<!DOCTYPE html>`이 없어 브라우저가 호환 모드로 렌더링. **2020년 원본부터** 없었다 | 레이아웃 맨 앞에 DOCTYPE 추가 |
| 카드 안 글자가 전부 파란색 | 카드 전체를 `<a>`로 감싸서 링크 색이 상속됨 | `a.card { color: var(--body) }` |
| 로컬 서버가 응답 없이 멈춤 | 파일을 지우는 도중 빌드가 실패한 뒤 다음 요청이 계속 대기 | `wrangler dev` 재시작 |
| 수집은 되는데 통계 경기 수가 거의 안 늘어남 | 낮은 티어에는 오래 쉰 플레이어가 많아서, "최근 경기 5개"가 몇 달 전(2월) 경기였다. 14일 통계에도 안 들어가고 곧 삭제될 경기만 쌓임 | `match-v5`에 `startTime`(14일 전)을 붙이고, 비활성 플레이어를 빼고, 시즌 판수가 많은 플레이어 위주로 고름. 한 번에 4개 → 8개 |
| 로컬에서 수집을 다섯 번 돌렸는데 경기는 11개 | `/__scheduled` 테스트 경로가 시간 값을 무시해서 다섯 번 모두 같은 구간·같은 플레이어 | 중복은 `upsert … ignoreDuplicates`로 걸러짐. 운영 Cron은 실행 시각으로 구간이 바뀜 |

## 6. 1편 vs 2편

| | 1편 (되살리기) | 2편 (개편) |
|---|---|---|
| 로그인 | Supabase Auth 이메일 | **없음** |
| 기능 | 전적 검색, 팁, 유저매칭 | **소환사 분석(장단점·추천), 챔피언 티어, 챔피언 정보** |
| 데이터 | 검색된 경기만 | **5분마다 티어별 자동 수집** + 검색된 경기 |
| 저장 | match-v5 원본 JSON (약 85KB/경기) | **분석용 행만** (약 3.5KB/경기), 30일 보관 |
| 집계 | 앱에서 | **Postgres 함수** |
| 디자인 | MDB Bootstrap (2019) | **DESIGN.md 토큰 기반 자체 CSS** |
| 정적 파일 | 약 8MB | **CSS 16KB** + 엠블럼 이미지 |

## 7. 느낀 점

- **"알아서"도 결국 질문에서 시작된다.** AI가 기획안과 선택지를 먼저 보여 줘서, 내가 정할 것(수집 여부, 콘텐츠 범위)과 AI가 정할 것(지표, 임계값, 저장 구조)이 깔끔하게 나뉘었다.
- **모르는 도구는 실행 전에 읽게 하자.** `npx` 한 줄도 남의 코드를 내 컴퓨터에서 돌리는 일이다. AI가 소스를 먼저 읽고 "파일 하나 쓰고 집계 요청 한 번"이라고 확인해 준 게 좋았다.
- **분석 사이트의 정직함은 "데이터가 없다"고 말하는 데서 나온다.** 처음 배포했을 때 티어표는 비어 있었고, 장단점 칸에는 "수집 중"이 떠 있었다. 대신 그 자리를 지어낸 숫자로 채우지 않았다.
- **6년 전에도 지금도 결국 용량과 한도의 문제다.** 2020년의 한계점은 "데이터를 매번 가져와 느리다, DB 비용이 부담된다"였다. 이번에는 축약 저장과 Cron으로 같은 문제를 무료 요금제 안에서 풀었다.
